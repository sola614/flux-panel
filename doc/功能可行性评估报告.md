# flux-panel 四项功能可行性评估报告

> 评估范围：`install.sh`、`go-gost/`（节点二进制源码）、`springboot-backend/`、`vite-frontend/`
> 评估日期：2026-10-12

---

## 结论速览

| # | 功能 | 结论 | 一句话理由 |
|---|------|------|-----------|
| 1 | install.sh 兼容 Alpine 等发行版 | ✅ **可行** | 参考脚本已给出完整 POSIX/OpenRC 实现，属"移植 + 补漏"，无架构障碍 |
| 2 | 转发/隧道/节点 批量删除 | ⚠️ **部分可行** | 单条删除逻辑完备可复用，但**前后端均无任何批量基础**，需新增接口 + 多选 UI |

## 一、install.sh 改造为兼容 Alpine 等主流发行版

### 结论：✅ 可行

### 现状（`D:/project/flux-panel/install.sh`，共 373 行）
- Shebang 为 `#!/bin/bash`，且大量使用 bash 专有语法：`[[ ]]`、`read -p`、`&> /dev/null`、`$EUID`、`getopts`。Alpine 默认只有 busybox `ash`，**没有 bash**，脚本无法直接运行。
- 服务管理**硬编码 systemd**：`/etc/systemd/system/gost.service`、`systemctl daemon-reload/enable/start`（L215-244、L300-319）。Alpine 用 OpenRC，无 `systemctl`。
- **硬依赖 curl**：L28、L179、L263 直接调用 `curl`，无 wget 回退、无自动安装。
- 发行版检测只存在于 `check_and_install_tcpkill()`（L83-121），且只用于装 `dsniff`，主流程未按发行版分流。
- **存在 bug**：`main()` 的 `case 4)` 调用了一个**从未定义**的 `block_protocol` 函数（L355）；同时菜单只显示 1-4（L41-46），而 case 却处理到 5，菜单与逻辑不一致。
- 无 root/提权处理、无 `/dev/tty` 交互回退（`curl | sh` 场景下 `read -p` 会失败）。

### 参考脚本（sola614/Sundries `flux_install.sh`）已具备
`#!/bin/sh` POSIX 化、`detect_distro`、`detect_init`（systemd/openrc/none）、`service_*` 抽象层（含 OpenRC `openrc-run` 脚本 + pidfile + 日志）、`install_pkg`（apt/apk/dnf/yum/pacman/zypper/emerge/xbps）、`download_file`（curl→wget）、`ensure_download_tool`、`prompt_read`（/dev/tty 回退）、`init_privilege`/`ensure_root`（sudo/doas）、Alpine 无 dsniff 的降级提示。

### 关键文件与模块
| 文件 | 作用 |
|------|------|
| `install.sh` | 需重写主体 |
| `springboot-backend/.../service/impl/NodeServiceImpl.java` L359-378 | 后端生成安装命令，硬编码 release URL 与 `-a/-s` 参数（改造后需保持参数兼容） |
| `go-gost/main.go` L122 | 节点上报版本号硬编码为 `"1.2.4"`，与 release `1.4.3` 不一致（顺带记录） |
| `panel_install.sh` | 面板端脚本，Docker 方式，**同样无 Alpine 检测**；本次不在范围，但若要求 Alpine 面板需另做 |

### 主要改动点
1. 改写为 POSIX sh（busybox ash 可跑），去掉 bash 专有语法。
2. 新增 `detect_init` + `service_install_file/service_start/service_stop/service_enable/service_disable/service_reload` 抽象，覆盖 systemd 与 OpenRC 两套。
3. 新增 `install_pkg` / `download_file` / `ensure_download_tool` / `prompt_read` / `ensure_root` 工具函数。
4. Alpine 分支：`apk add --no-cache`；`dsniff` 官方仓库没有 → 优雅跳过并提示。
5. 修复 `block_protocol` 未定义、菜单编号不一致两个既有缺陷。
6. 保持 `/etc/gost` 目录、`config.json`/`gost.json` 路径与 `-a/-s` 命令行约定不变，保证后端生成的命令继续可用。

### 潜在风险
- **二进制兼容性**：gost 为 Go 静态编译，musl 下通常可直接运行；但需实测 release 产物在 Alpine 上的可用性。
- **tcpkill 功能缺失**：Alpine 无 dsniff 包，"协议屏蔽"能力在该系统上不可用（需自行编译 dsniff）。
- **OpenRC 细节**：`command_background=yes` + `pidfile`、日志需自行 `: >` 初始化；无 systemd 的 `Restart=on-failure` 语义，需靠 `supervise-daemon` 或 `respawn`。
- **`delete_self` 在 `curl | sh` 下 `$0` 可能是 `sh`**，需沿用 readlink/realpath 回退并谨慎判断。
- 国家识别依赖 `ipinfo.io`，无网时镜像加速分支失效（非致命）。
- 版本号不一致（1.2.4 vs 1.4.3）建议一并核对。

## 二、转发 / 隧道 / 节点 批量删除

### 结论：⚠️ 部分可行
单条删除链路完整、可复用；**批量属于纯增量开发**，没有结构性阻塞，但**现有接口与前端都没有任何批量基础**。

### 现有接口（均为"单 id"）
| 模块 | 接口 | 签名 | 权限 |
|------|------|------|------|
| 转发 | `POST /api/v1/forward/delete` | `Map{id}` → `deleteForward(Long)` | 逐条校验（管理员 or 普通用户隧道权限） |
| 转发 | `POST /api/v1/forward/force-delete` | `Map{id}` | 同上，跳过 gost 删除 |
| 隧道 | `POST /api/v1/tunnel/delete` | `Map{id}` | `@RequireRole`（管理员） |
| 节点 | `POST /api/v1/node/delete` | `Map{id}` | `@RequireRole`（管理员） |

> 全仓 grep `batch|List<Long>|removeByIds` 后确认：**后端不存在任何批量删除接口**，`removeByIds` 从未使用。

### 现有服务逻辑（可复用点）
- `ForwardServiceImpl.deleteForward`（L246-293）：校验存在性 → 取隧道 → **逐条权限判断**（`roleId != ADMIN` 时校验 `UserTunnel`）→ `deleteGostServices`（经 WS 调用节点）→ `removeById`。单条逻辑已封装良好。
- `TunnelServiceImpl.deleteTunnel`（L232-247）：先 `checkTunnelUsage`（有转发/用户权限则拒绝）。
- `NodeServiceImpl.deleteNode`（L183-199）：先 `checkNodeUsage`（作为入口/出口节点被引用则拒绝）。

### 前端基础：**不具备**
- `vite-frontend/src/api/index.ts`：`deleteForward/deleteTunnel/deleteNode` 均接收**单个 id**。
- `forward.tsx`（L474 `handleDelete`）、`tunnel.tsx`（L231）、`node.tsx`（L445）均为**逐行卡片删除 + 确认弹窗**，列表以 `Card` 渲染（非 Heroui `Table`），**没有勾选/多选**。
- 页面里的 `selectedTunnel / selectedTunnelForExport` 等是**表单下拉**状态，与列表行选择无关。
- `components/primitives.ts` 未封装表格组件，列表页各自直写。

### 主要改动点
1. **后端新增批量接口**：如 `POST /forward/batch-delete`、`/tunnel/batch-delete`、`/node/batch-delete`，请求体 `{ ids: [...] }`；内部循环调用既有单条逻辑，聚合"成功/失败明细"。
2. **返回结构**：建议 `{ successCount, failCount, failures:[{id, reason}] }`，支持部分成功语义。
3. **前端多选**：卡片列表加 checkbox 或改用 Heroui `Table` 的 `selectionMode="multiple"`；新增批量操作条 + 二次确认；调用批量接口并按明细提示。
4. 权限沿用各模块既有规则（转发逐条、隧道/节点 `@RequireRole`）。

### 潜在风险
- **部分失败语义**：隧道/节点有依赖检查、转发依赖节点在线，批量必然出现部分成功，需明确提示与重试。
- **性能**：转发删除需经 WS 调节点，`WebSocketServer.send_msg` 单次超时 **10s**（L473），批量 N 条可能长时间阻塞 → 建议异步化 / 并发 / 进度反馈。
- **事务边界**：gost 服务删除是外部副作用，DB 事务回滚**无法撤销**节点侧已删服务，不能简单套 `@Transactional`。
- **审计**：批量接口需挂 `@LogAnnotation`，并在日志中记录 id 列表。
- 前端分页/搜索/分组状态与"全选"的交互需单独设计。

## 三、节点监控简化上报（仅在线）+ 64M Alpine 稳定

### 结论：✅ 可行（低风险）
**关键发现**：节点"在线/离线"状态**本就与定时上报无关**——它由 WebSocket 连接生命周期决定（`WebSocketServer.afterConnectionEstablished` 置 `status=1`，`afterConnectionClosed` 置 `status=0`）。当前每 2 秒的上报**仅用于监控图表**（CPU/内存/网络/uptime）。因此"仅上报在线"本质上等于：**保留 WS 连接，砍掉/大幅降频重量级指标采集**。

### 现状（`go-gost/x/socket/websocket_reporter.go`）
- `pingInterval = 2 * time.Second`（L121），每 2 秒 `collectSystemInfo()` 后 `sendSystemInfo()`。
- `collectSystemInfo`（L298-310）每次采集：
  - `getCPUInfo()` → `cpu.Percent(time.Second, false)`（L1020）——**每次阻塞 1 秒**，产生大量分配。
  - `getMemoryInfo()` → `mem.VirtualMemory()`。
  - `getNetworkStats()` → `psnet.IOCounters(true)`（遍历所有网卡）。
  - `getUptime()` → `host.Uptime()`。
- 依赖 `github.com/shirou/gopsutil/v3`（`go.mod` L98，间接依赖），体积与分配开销不小。
- 服务端 `WebSocketServer.handleTextMessage` L79：用 `decryptedPayload.contains("memory_usage")` 判断并回 ack（L81）。**改上报内容必须同步改这里**。
- 前端 `node.tsx` 消费 `cpu_usage/memory_usage` 等字段展示（grep 命中），字段变化需同步。
- 启动点：`go-gost/main.go` L122 `StartWebSocketReporterWithConfig(..., "1.2.4")`。

### 关键文件与模块
| 文件 | 关注点 |
|------|--------|
| `go-gost/x/socket/websocket_reporter.go` | 上报主体：`handleConnection` / `collectSystemInfo` / `getCPUInfo` / `getNetworkStats` / `sendSystemInfo` |
| `go-gost/main.go` | 上报器启动、版本号 |
| `springboot-backend/.../utils/WebSocketServer.java` | `memory_usage` 分支、连接生命周期改状态 |
| `springboot-backend/.../dto/SystemInfoDto.java` | 上报字段定义 |
| `vite-frontend/src/pages/node.tsx` | 监控展示，字段依赖 |
| `install.sh`（服务定义） | 内存限制 / 环境变量注入 |

### 主要改动点
1. **上报瘦身**：把 2s 全量指标改为轻量心跳（例如 30–60s 一次，或不发业务负载、仅靠 WS ping/pong）。`SetReadDeadline(30s)` 已存在，可加 `SetPingHandler`。
2. **去掉/替换 gopsutil**：移除 `cpu/host/mem/net` 引用；若仍需极少指标，直接读 `/proc/meminfo`、`/proc/net/dev`，并**删除阻塞 1 秒的 `cpu.Percent`**。
3. **服务端同步**：`handleTextMessage` 的 `contains("memory_usage")` 判断改为匹配新心跳格式（或直接走连接生命周期，不依赖负载）。
4. **前端同步**：`node.tsx` 若不再有 CPU/内存数据，需隐藏对应图表或显示"—"。
5. **64M 稳定性**：
   - 服务注入 `GOMEMLIMIT`（如 `GOMEMLIMIT=40MiB`）与 `GOGC` 调优；
   - 降低 tick 频率、避免阻塞采集；
   - systemd 用 `MemoryMax=`，OpenRC 无原生 cgroup，需靠环境变量 + 系统级限制。
6. 需**重新编译并发布节点二进制**（release 1.4.3），install.sh 下载的是发布产物。

### 潜在风险
- **联动改动面**：服务端字符串匹配 + 前端字段展示，两处必须同步，否则 ack 或图表异常。
- **需重新发版**：go-gost 是 fork，改动后必须重编译并更新 release，安装脚本才会生效。
- **64M 的真实瓶颈**：Go runtime 基线 + gost 代理负载才是内存大头，上报器只是贡献者之一；`GOMEMLIMIT` 是**软限制**，goroutine/分配尖峰仍可能 OOM。建议先实测 RSS，再决定是否配合 cgroup 硬限制 / swap。
- 版本号 1.2.4 与 release 1.4.3 不一致，建议顺带统一。

## 四、用户管理权限分支的批量处理

### 结论：✅ 可行
"权限分支"指用户卡片上的**「权限」按钮**打开的**隧道权限管理弹窗**（`user.tsx` L858+），内含「分配新权限」与「已有权限」表格。后端已有清晰的单条 assign/remove 与级联删除逻辑，批量属增量。

### 现状
- **接口**（`TunnelController.java`）：
  - `POST /tunnel/user/assign`（`UserTunnelDto`，单隧道）
  - `POST /tunnel/user/list`（查询）
  - `POST /tunnel/user/remove`（`{id}`，**单条**）
  - `POST /tunnel/user/update`
  - 以上均带 `@RequireRole` → 仅管理员。
- **服务**（`UserTunnelServiceImpl`）：
  - `assignUserTunnel`（L84-101）：查重后 `save`，默认 `status=1`。
  - `removeUserTunnel(Integer id)`（L123-141）：先 `removeUserTunnelForwards(userId, tunnelId)` **级联删除该用户在该隧道下的所有转发及 gost 服务**，再删权限行。
- **权限校验方式（两层）**：
  1. **角色层**：`@RequireRole` + `RoleAspect` 强制 `role_id == 0`（管理员），否则 403。
  2. **业务层**：转发模块对普通用户做隧道权限/到期校验（`ForwardServiceImpl`），而用户隧道权限接口本身是管理员专属，无"归属校验"。
- **前端**（`user.tsx`）：`handleManageTunnels` 打开弹窗；「分配新权限」用**单选** `Select` 选隧道（L884）；「已有权限」表格（L989）每行一个删除按钮（`handleRemoveTunnel` L427 → `removeUserTunnel({id})`）。**无多选**。

### 批量处理的粒度（建议）
| 粒度 | 说明 | 推荐 |
|------|------|------|
| 同一用户 · 多隧道权限 | 在权限弹窗内勾选多行「已有权限」批量移除 | ★ 最自然，贴合现有弹窗 |
| 同一用户 · 多隧道分配 | 「分配新权限」改多选，一次分配多个隧道 | ★ 配套 |
| 跨用户批量 | 用户列表勾选多用户 → 批量删除/重置/改权限 | 进阶，需新增列表多选 |

### 权限校验方式（批量）
- 新批量接口继续挂 `@RequireRole`（管理员专属）。
- 服务内**逐条**执行既有逻辑（查重/级联删除），**建议校验每条权限记录归属目标用户**（现有 `removeUserTunnel(id)` 未校验归属，批量场景下应补 `user_id` 校验以防越权）。
- 返回聚合结果（成功/失败明细）。

### 关键文件与模块
- `springboot-backend/.../controller/TunnelController.java`（L75-118）
- `springboot-backend/.../service/impl/UserTunnelServiceImpl.java`
- `springboot-backend/.../common/annotation/RequireRole.java` + `common/aop/RoleAspect.java`
- `vite-frontend/src/pages/user.tsx`（L427、L858-1099）、`vite-frontend/src/api/index.ts`（L46-49）

### 主要改动点
1. 新增 `POST /tunnel/user/batch-remove`（`{ids:[...]}`）与 `POST /tunnel/user/batch-assign`（`{userId, tunnelIds:[...]}`）。
2. 服务层循环复用单条逻辑，聚合结果；批量移除需带 `userId` 归属校验。
3. 前端：「已有权限」表格开启 Heroui `selectionMode="multiple"` + 批量移除按钮；「分配新权限」改多选 `Select`。
4. 批量接口挂 `@LogAnnotation` 审计。

### 潜在风险
- **级联 gost 删除慢**：每删一条权限都要逐个调节点删转发，批量耗时长 → 需进度/超时/部分失败提示。
- **归属校验缺口**：现有单条 `remove` 按 id 删除、不校验归属，批量必须补上，否则存在越权风险。
- **响应聚合**：现有统一返回单个 `R`，批量需定义明细结构。
- **前端交互**：弹窗内单选框改多选、部分失败提示、表格全选状态管理。

## 附：跨项共性提示

- **批量类功能（2/4）共用模式**：后端"新增批量接口 + 循环复用单条 + 聚合结果"，前端"列表多选 + 批量操作条 + 二次确认"，权限沿用各模块既有规则。
